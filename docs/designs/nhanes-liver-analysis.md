## Problem Statement

Build a work sample for a Research Data Analyst role in the UCSF Division of
Gastroenterology and Hepatology, demonstrating competence with clinical survey data by
a mathematics graduate with no clinical background.

Analytic question: in the US adult population, what is the prevalence of hepatic
steatosis, and what is the adjusted association between metabolic factors (BMI, HbA1c,
age, sex, race/ethnicity) and CAP, estimated with correct design-based standard errors?

The deliverable is a documented, reusable analytic dataset. The model is the vehicle
that proves the dataset is trustworthy, not the point. This replicates established
findings, stated plainly in the README.

## What Makes This Good

Three things separate it from a generic NHANES notebook:

1. A **validation-rules table** as a first-class artifact: one row per variable with
   type, allowed range, NHANES missing codes, n missing, n out of range, action taken,
   and a recommendation. This is the job posting's "range and quality checks and
   recommendations for revising procedures" delivered as an artifact rather than a claim.
2. A **naive-versus-weighted comparison** showing how far unweighted standard errors are
   wrong. That specific failure mode is why a GI/Hep group hires an RDA.
3. A **longitudinal-modeling specification** for a requirement NHANES cannot satisfy:
   why NHANES is repeated cross-sectional and not longitudinal, and what model would be
   fit for a repeated-FibroScan cohort (GEE with exchangeable working correlation for
   population-average change, versus a mixed model with random intercepts for
   subject-specific trajectories, and when each applies). **Written, not demonstrated on
   simulated data.** Fabricating a dataset to exercise a keyword is the failure mode this
   project's own brief warns against, and a repo that is otherwise all real NHANES data
   should not contain one section modeling numbers that were invented. Naming the gap
   precisely is the demonstration.

A fourth thing, which emerged during design rather than being planned: the project has a
**real methodological finding**. The `5.397605e-79` artifact is not confined to a count
variable in `P_LUX`; it is in `WTMECPRP`, the examination weight, where it encodes the
1,260 zero-weight participants. Any zero-weight check written against that variable
returns nothing. That is a genuine "recommendation for revising procedures," found by
doing the range checks the job posting asks for.

## Premises

Agreed:

1. The deliverable is a documented, reusable dataset; the model proves the dataset is
   trustworthy.
2. Day 1 must ship. SQLite is the designated cut line; the exclusion log is not cuttable.
3. R earns its place, because `svydesign`/`svyglm` is the reference implementation a
   hepatology biostatistician expects. But the R install moves to minute zero and runs
   in the background, and the Day 1 ship gate does not depend on it.
4. Build the survey design on the FULL data, then subset the design object. Never filter
   the dataframe first. Count exclusions on the raw dataframe for the log; run all
   estimation through the subset design.
5. Left joins only, starting from `P_DEMO`. Assert row count unchanged after each join.
6. Never exclude on outcome magnitude. High stiffness is the disease. Exclude on quality
   and eligibility. If values look extreme, flag rather than delete: keep in the primary
   model, refit once without them as a sensitivity check, report both.
7. Age is top-coded at 80. The age coefficient is compressed at the top. Note as a limitation.

Revised during this session:

8. **ALT does not belong on the right-hand side of a CAP model.** Causal order is
   BMI → hepatic fat → hepatocyte injury → ALT release. ALT is downstream of the
   outcome. Adjusting for it blocks part of the BMI path and attenuates the headline
   coefficients. ALT/AST/GGT become secondary outcomes and a descriptive table.
9. **"How much of the variation is explained" is not estimable here.** Design-based
   regression estimates finite-population parameters, not a variance decomposition.
   `svyglm` deliberately returns no R². Primary outputs become weighted prevalence with
   design-based CIs, plus adjusted coefficients. Any R² is a descriptive footnote,
   labelled as such.
10. **`LUAXSTAT == 1` is a stiffness-quality criterion, not a CAP-quality one.**
    Verified against the local `P_LUX.XPT`: **677 participants have a valid `LUXCAPM`
    but `LUAXSTAT != 1`**, all from `LUAXSTAT == 2` (partial exam). The mechanism, that
    stiffness IQR/median degrades with body habitus, is a **hypothesis, not a verified
    finding**: `P_LUX` carries no anthropometry. Add a 15-minute check after the `P_BMX`
    merge regressing both `LUXSIQRM` and `LUXCPIQR` on `BMXBMI`. If both slope, CAP-
    specific quality does not fully remove the selection problem, and that goes in
    limitations. If only stiffness slopes, premise 10 is confirmed empirically, which is
    stronger than asserting it. The CAP sample is defined by non-missing `LUXCAPM`
    plus CAP-specific IQR quality (`LUXCPIQR`). `LUAXSTAT == 1` is retained as a column
    and used only for analyses of `LUXSMED`.
11. **The 274.2 / 254.4 CAP benchmark is a sanity check, not a gate.** (274.2 as a
    published *mean* and 274 as a *steatosis threshold* are unrelated quantities that
    collide numerically. Cite the threshold separately and say so in one sentence, or a
    reader concludes you used a population mean as a cutpoint.) It comes from an
    NHANES 2017–2018 analysis of adults 20+, a different release under different
    COVID-adjusted weights. A few dB/m of offset is expected and is not a bug. The
    design object is validated instead against a statistic published from the same
    `P_` files and the same `WTMECPRP` weight.

Retained against challenge:

12. **HbA1c stays in the primary model.** The cold read is mechanically right that
    `LBXGH` partly mediates BMI → steatosis, but that reasoning taken to its conclusion
    strips the model to BMI and demographics, and the job asks for a defended
    multivariable model. Keep it and name it as a mediator in the limitations. Being
    explicit that the BMI coefficient is a direct effect is the demonstration; silently
    dropping the variable is not.

## Verified findings (this session, against real data)

### The artifact is in the survey weight

**`WTMECPRP` contains 1,260 `5.397605e-79` values.** These are the interviewed-but-not-
MEC-examined participants whose examination weight is zero. Two consequences:

1. **`WTMECPRP == 0` matches zero rows.** Any zero-weight guard, any "was this person
   examined" check written against the weight, silently returns nothing.
2. **If `svydesign` is built before the artifact is fixed, 1,260 participants enter the
   design with a weight of 5.4e-79 instead of 0.** Point estimates survive; the design
   object's own accounting does not.

It is also in `RIDAGEYR` (574 rows, infants under one year), `INDFMPIR` (142 rows,
poverty ratio 0.0), and `RIDAGEMN` (57 rows). The `RIDAGEYR >= 18` filter happens to
work anyway because 5.4e-79 < 18, but `describe()` on age is corrupted until it is fixed.

**Therefore the artifact sweep is step one of the pipeline, before the joins, before the
cascade, before the design object.** Not a cleaning step inside `02_clean_qc.py`.

### P_LUX specifics

- `P_DEMO` shape: 15,560 × 29, all `SDDSRVYR == 66`. **10,409 of those 15,560 have a
  `P_LUX` record**, which is the join arithmetic the cascade must reflect.
- `RIDRETH3` has six levels: 1 (1,990), 2 (1,544), 3 (5,271), 4 (4,098), 6 (1,638),
  **7 (1,019)**. There is no level 5. **Level 7 is "Other Race, Including Multi-Racial,"
  a real category, not a missing code.** A blanket "recode 7/9/77/99 to NA" sweep deletes
  1,019 people from a model that adjusts for race. `RIDAGEYR == 80` is likewise a
  top-code, not a refusal.
- `INDFMPIR` is missing for 2,201 of 15,560 (**14.1%**), higher than commonly assumed.
  It stays out of the model and goes into the missing-data comparison.
- `P_LUX` shape: 10,409 × 13. `LUAXSTAT`: 9,023 complete / 748 partial / 386 ineligible
  / 252 not done. Matches the brief.
- `LUXCPIQR` (CAP IQR) exists and is the CAP-specific quality variable.
- `LUXCAPM` non-null: 9,698. Valid CAP with `LUAXSTAT == 1`: 9,021. **Valid CAP with
  `LUAXSTAT != 1`: 677.**
- The `5.397605e-79` artifact appears in **five** columns, not one:
  `LUANMTGP` (671), `LUXCPIQR` (80), `LUXSIQR` (27), `LUXSIQRM` (12), `LUANMVGP` (2).
  Two of those are quality variables the pipeline filters on. The QC step must scan
  every float column for it, not fix only the known case.
- **All 677 recovered participants come from `LUAXSTAT == 2` (partial exam).** None come
  from ineligible (3) or not-done (4), which have zero CAP readings by construction.
  CAP availability by status: 1 → 9,021/9,023; 2 → 677/748; 3 → 0/386; 4 → 0/252.
- **The recovered group's CAP measurement quality is indistinguishable from the kept
  group's.** Median `LUXCPIQR`/`LUXCAPM` ratio is 0.1359 for the recovered 677 versus
  0.1357 for the 9,021 already kept; 11.8% versus 8.9% exceed a 0.30 ratio. This is the
  empirical case that the `LUAXSTAT == 1` drop was a stiffness-criterion artifact and
  not a CAP-quality judgment. It is also the strongest single paragraph in the README.
- **The two `LUAXSTAT == 1` records with missing `LUXCAPM`** (SEQN 109319, 121297) both
  have valid stiffness (`LUXSMED` 5.3 and 5.8) and 15 and 10 valid measures respectively.
  The exam was complete for stiffness; CAP simply was not returned. Account for them in
  the cascade as "complete exam, CAP not returned," not as a data error.
- **The artifact maps to 0 in all five columns, and the brief was right.** The evidence:
  no genuine exact-zero values exist anywhere in the non-artifact data for the three IQR
  variables (their true minima are 1.0, 0.1, and 0.8), so the artifact is the encoding of
  zero. The artifact rows in `LUANMTGP` are 386 ineligible + 252 not-done + 33 partial,
  exactly the people with no measures attempted.
- **A CAP interquartile range of zero is real, and it is a censoring detector.** Of the
  60 complete exams with a zero `LUXCPIQR`, **47 have `LUXCAPM` pinned at exactly 400
  dB/m**, the device ceiling. When every reading saturates at the maximum, the IQR is
  genuinely 0. These are not quality failures; they are the most steatotic participants
  in the sample.
- **Therefore: CAP is censored at both device bounds.** 163 participants (1.68%) sit at
  exactly 400 dB/m and 40 (0.41%) at exactly 100; 252 are at or above 390. Liver
  stiffness is censored too, though negligibly: 9 at the 75.0 kPa ceiling, 1 at the
  1.6 kPa floor. A linear model on a right-censored outcome attenuates the slope at the
  top, which means the BMI coefficient is a conservative estimate. This belongs in
  limitations, and the ceiling count belongs in `validation_rules.csv`. It is also the
  right place to note that this is a censoring problem, not an outlier problem, so
  premise 6 still holds: flag, never delete.
- **Range check flag: `LUXSIQRM` reaches 1338%** (median 13.1, 99th percentile 49.1).
  Ratios above 100% are arithmetically possible when the median stiffness is very low,
  but this is the kind of value the validation-rules table exists to surface. Flag, do
  not delete, per premise 6.
- Confirmed device bounds: `LUXCAPM` spans exactly 100–400 dB/m and `LUXSMED` spans
  1.6–75.0 kPa, both matching the brief. These become explicit range-check rules.
- **Unit trap: the two IQR quality variables are on different scales.** `LUXSIQRM` is
  already a percentage (observed values like 17.0 and 25.9), so NHANES's completeness
  rule is `LUXSIQRM < 30`, not `< 0.30`. `LUXCPIQR` is an absolute IQR in dB/m and must
  be divided by `LUXCAPM` to get a comparable ratio. Writing `LUXSIQRM < 0.30` would
  silently drop essentially the entire sample. This belongs in `validation_rules.csv`.

## Validation target (confirmed this session)

The design object is validated against NCHS's own published estimates from the **same
`P_` files and the same examination weight**, reported in National Health Statistics
Report 158 (June 2021):

| Outcome | Population | Age-adjusted prevalence | 95% CI |
|---|---|---|---|
| Obesity (`BMXBMI >= 30`) | adults 20+ | **41.9%** | 39.4–44.3 |
| Severe obesity (`BMXBMI >= 40`) | adults 20+ | 9.2% | 8.0–10.6 |
| Hypertension | adults 18+ | 45.1% | 42.5–47.6 |

**The wrinkle: these are age-adjusted, not crude.** Reproducing 41.9% requires direct
standardization to the 2000 projected U.S. Census population using the report's age
groups (20–39, 40–59, 60+). A plain `svymean` of `BMXBMI >= 30` will not land on 41.9%
and a mismatch would not indicate a bug. This costs roughly 20 extra minutes and is
worth it: direct age standardization is a real biostatistics skill and it is a much
tighter test of the design object than the cross-release CAP comparison.

NCHS does not publish a crude adult obesity prevalence in this report, so age
standardization is not optional if this is the check.

**Do not use the diabetes figure (14.8%) as a check.** NCHS computed it with morning
fasting sample weights, not the MEC weight, so it cannot validate a `WTMECPRP` design
object. Hypertension (45.1%, MEC weights, adults 18+) is the natural second check.

**Note on this release: the PSU and strata variables are masked.** NCHS masked
`SDMVPSU`/`SDMVSTRA` specifically to prevent analysts from separating the combined file
back into its component cycles. They still work correctly for Taylor-linearized variance
estimation, which is the method NCHS itself used. Worth one sentence in the README,
because it is a data-management detail that shows you read the release documentation.

Sources: [NHSR 158](https://www.cdc.gov/nchs/data/nhsr/nhsr158-508.pdf),
[NCHS prepandemic file development report](https://www.ncbi.nlm.nih.gov/books/NBK606854/)
